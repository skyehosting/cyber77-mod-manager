# Group Mods, Saves selection and Trash, the Mods toolbar: decisions (2026-11-06)

Mockups: `.toolkit/design/` of the toolkit workspace (mods-header, saves-1..3, group-1..3, group-flows,
group-mods-plan). Chosen by the operator.

## Mods toolbar
- The header row holds only the title (and, when Group Mods ships, the **two-segment pill** Mods | Group Mods).
- Search row: search, filter, category, sort, Install from file, **⋯** (beside the dropdowns), then
  **Expand all** at the far end. The operator asked for ⋯ and Expand all swapped from the mockup.
- ⋯ holds Update all (with a count on the ⋯ button while updates wait), Check for updates, Deploy
  REDmods, Redeploy, Open game folder, Disable all.

## Saves
- **Saves 2's look** (a checkbox on the thumbnail, shown on hover and on every row once anything is
  ticked; nothing else changes on the page) with **Saves 1's floating bar** at the bottom: "1
  playthrough, 2 saves selected (5 saves, 25 MB) · Copy to… · Move to… · Delete · ×".
- Copy/Move: a profile picker. The source isn't offered; "already has 2 of 5" saves are skipped (same
  sav.dat). Move = copy, then the originals go to the Trash only once every target has them.
- Delete → **Trash** (a tab right of Backups). Restore (a taken slot gets the next free ManualSave
  number; a deleted profile asks where), Delete forever, Purge bin (asks, shows size). Game closed
  for anything that touches the game's folder.

## Group Mods (operator's answers to the plan)
1. Nexus mods always download from Nexus. Agreed.
2. **No P2P file sharing at all**: Nexus for everything ("use Nexus instead"). A non-Nexus file in a
   list shows as "not on Nexus: get it from <member>" (install from file; matched by hash).
3. Invite code instead of a raw IP, encrypted, host key pinned. Agreed.
4. No server. Agreed.
- **Direction: Group Mods 1** (lists rail + detail).
- **No dedicated group profile**: group mods install into the user's own setup. They show enabled in
  the normal Mods list too, and a toggle in Group Mods is the same toggle as on the Mods page (both
  views always agree). So "removed from the list → disabled" applies only to mods that came in through
  the group; a mod the user already had is left as it is (they're told).
- Installer (FOMOD) choices: shared.
- Win conflicts: the group's order is offered, the user can decide for themselves.
- Pinned versions: synced; the app checks the file still exists on Nexus, and the user can pick
  another version when several exist.
- Game version mismatch: shown. Requirements: as on the Mods page. Download size: shown.
- **Passcode per group**, generated by the app (the creator's app first), synced to members so any
  member can invite. Joining needs the invite code **and** the passcode. When a member leaves or is
  removed, the passcode rotates for everyone; a member who was offline gets the new one on launch from
  any member (members authenticate with their device keys, not the passcode), so an old passcode never
  works again.
- **Host**: whoever created it; if the host leaves, the next member (the longest-standing one, a rule
  every app works out the same way from the shared log) becomes host, offline members included when
  they next connect. Only the host can remove members; everyone else is equal. No further admin system.
- Limits: trust within the group. Hard limits stay only for connections not yet authenticated
  (strangers reaching the port).

## Phase 1 scope (built 2026-11-06)

Goal: friends share a mod list that stays in sync between their apps, and each one installs the list's
Nexus files through the app's normal download path after an OK.

Done means:
- Settings → Groups: on/off (off by default), port (47077), router port by UPnP (try, report), firewall
  step (Windows: one admin prompt adds/removes an inbound rule; Linux: shows the command), run in the
  background while in a group.
- Create a group (name, your name, first list), invite (code + passcode, one-time, 24 h), join (paste
  code, type passcode, preview, join), leave; the host can remove members; passcode rotates on leave or
  removal; host succession by the shared log.
- Lists: add mods from my installed Nexus mods (A–Z picker), remove, change version; each entry pins
  mod id + file id + version + requirements.
- Sync: a signed append-only event log per group, exchanged over an encrypted connection with the
  host's key pinned by the invite; any member relays; state = the log folded in order.
- Mods page: the Mods | Group Mods pill; Group Mods 1 layout (rail of groups/lists, the chosen list,
  Changes to review, my status per mod: Installed / Missing / Different version / Disabled / Only you).
- Review → Download selected (Premium: API; free: one-click pages), the requirement tree with boxes.
- Removed from a list → disabled, only if it came in through the group; waits for the game to close.
- Start-up toast with what changed (×, shrinking bar, hover pauses); a toast at game exit.
- Members: online, last seen, game version, sync state.
Non-goals for phase 1: installer (FOMOD) choices, conflict order, version picker beyond "the list's
version or the newest", share list as code, any file transfer between members.

## How phase 1 is built (src/core/groups) and why

- identity.js: an ECDSA P-256 key and a self-signed certificate per PC (the DER is built here, verified
  with node:crypto). P-256 because Electron 45's TLS (BoringSSL) refuses Ed25519 certificates and TLS-PSK
  (tested). The key is encrypted with safeStorage; an identity that can't be read is never replaced.
- net.js: TLS 1.3 both ways, each side pins the other's certificate fingerprint (no CA). Framed JSON;
  16 KB before admission, 8 MB after; handshake 10 s, hello 10 s, 300 frames / 10 s, 32 MB send
  backlog, per-address caps (IPv6 by /64), 512 connections; a ping every 40 s.
- log.js: a causal signed log. Each event names its parents and its counter must be 1 + the largest
  parent's; the group id is sha256(creator key + nonce) so only its creator can make it; per-type data
  keys only, 12 KB per event; 1000 counted events per member; a member other than the host lets in at
  most 4 people counted over everyone below them; a departure cuts what the departed signed that the
  departure does not build on; a new passcode counts only if it is new, ≥16 characters and built on
  the latest departure; only the host removes and only the host re-admits someone removed.
- service.js: joins need a one-time invite token (stored hashed) and the passcode; the history goes in
  1 MB pieces; events waiting for parents are capped (50 per member, 200 in all) and signature-checked;
  removed members get only their own removal and then nothing; "have" every 10 minutes.
- firewall.js: Windows: one UAC prompt, PowerShell by its System32 path with -EncodedCommand (no
  script file); Linux: ufw / firewalld commands, pkexec by absolute path.
- upnp.js: SSDP + SOAP, answers held to the responding private IPv4 host; finite 1 h lease, renewed;
  removed when groups go off and on quit (quit waits up to 3 s).

Audits (2026-11-06): two security reviews and two bug reviews, every finding fixed and re-verified
(reproductions went red → green). Accepted, low: the router's reported internet address is trusted; a
list entry holds one file per mod; replacing a version applies in every profile (as updates do); a
Main plus a separate Update file of one mod are left side by side (two candidates, nothing replaced).
Not done yet: running in the background (tray) while in a group; installer (FOMOD) choices, conflict
order, version picker (phase 2).
